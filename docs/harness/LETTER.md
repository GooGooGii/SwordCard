## 使用者沒問、但我認為對這個環境最重要的三件事

### 1. 最大的實際風險不是寫錯程式，是弄丟未 commit 的工作

這個環境的特殊性：使用者常**同時開第二個 session 跑美術管線**（見 memory「並行 session 防撞守則」），
工作樹經常有 9+ 個未 commit 的修改檔（本 session 開場就是如此）。這代表：
- 你看到的 modified 檔案**不一定是你的**——動手前 `git status --short`，只碰你任務相關的檔
- 任何 `git checkout --` / `reset --hard` / stash drop 都可能毀掉另一個 session 幾小時的工作——這類指令沒有使用者明確要求絕不跑
- 你自己做完一個邏輯單位就**建議 commit**（訊息格式照 conventional commits）；session 隨時可能中斷，落檔＋commit 的才是使用者真正拿到的

### 2. `main.gd`（12,000+ 行 god object）是對小模型傷害最大的技術債，值得主動提議分拆

Fable 可以在腦中持有這個檔案的大概結構，Sonnet 級模型做不到——所以每次動 main.gd 都是這個環境出錯率最高的操作。
CLAUDE.md 的鐵律（Grep 定位 → 片段讀）只是止血。真正的解法是把 screen 建構逐個抽成獨立控制器
（專案自己也在 Project Layout 註記「待抽 screen 控制器」）。如果使用者有意願，安全的做法：
- 一次只抽**一個** screen（如 bestiary 或 shop），用重構模板（DELEGATION_TEMPLATES §3）：前後 smoke 都綠、行為零改變
- 抽完立刻 commit，再抽下一個；不要一口氣大重構
- 每抽掉一塊，之後所有 session 的出錯率都降一點——這是複利最高的工程投資

### 3. 平衡調整走數據管線，品味調整走多案送選——別搞反

這個 repo 已經有罕見完整的平衡基建：`BattlePolicy` deterministic 模擬、30 場固定 seed regression、
`tools/ai_run.gd` 全 run 驅動器、`docs/BALANCE_REPORT.md` 的歷史結論。
**數值問題永遠先跑模擬再下結論**，不要憑「感覺這張卡太強」動數字——歷史證明直覺會錯
（敵 HP ×2.4 三人隊勝率仍 97%，瓶頸其實在 tempo，這種反直覺結論只有模擬抓得到）。
反過來，**命名 / 文案 / 美術是品味題**，模擬幫不上忙、你的等級也補不上——照 JUDGMENT §3：多案＋使用者選。
分不清是哪類時：能寫出可測量判準的是數據題，寫不出的是品味題。

## 這套制度最可能的退化方式與預防

1. **沒人讀**（最可能）。規則檔存在但 session 直接開工。預防已內建：最致命的三條規則（鐵律）直接放在 CLAUDE.md 頂部隨 session 載入，路由表放最前面；其餘檔案按需讀。如果你現在在讀這句話，制度活著。
2. **只加不刪的通膨**。每次踩坑加一條，五十次後 CLAUDE.md 回到 999 行、重回「注意力稀釋」的老病。預防：MAINTENANCE §4 的行數上限與精簡流程；超標那次 session 就處理，不要拖。
3. **儀式化遵守**。照抄模板但不懂為什麼，於是在模板不適用時硬套（例：對一行 typo 修復也派 verifier）。預防：每條規則都附了動機；覺得規則在當下情境很蠢時，多半是情境不在規則射程內——用 JUDGMENT 的判準想一層，而不是機械執行或乾脆無視。
4. **規則與現實脫鉤**。重構後檔名變了、工具 schema 變了，規則還指著舊位置，於是整份文件失去公信力、被整體無視。預防：MAINTENANCE §5 每季抽查；發現一條失效就當場修（這是不用問的自由改動）。
5. **備份與 archive 被當垃圾清掉**。`docs/harness/backup/` 是唯一能回滾制度的東西。預防：列入 MAINTENANCE §2 紅線。

## 誠實條款：這套制度的極限

制度能補的：**執行品質**——不漏驗證、不燒 context、不重複踩坑、錯了知道何時停。
補不了的：
- **品味**（命名語感、文案、美術）——Sonnet+制度寫出來的仙俠文案就是比不上更強的模型。繞法：多案送選（JUDGMENT §3/§6）；真正重要的文案批次留給使用者用更強模型的 session 做。
- **跨系統的平衡直覺**——制度用模擬管線代償（見上第 3 件事），但「該往哪個方向調」的假設生成仍吃模型等級；假設錯了模擬只會告訴你結果不如預期，不會告訴你該試什麼。繞法：一次多試幾個方向的模擬、把結果寫回 BALANCE_REPORT 累積。
- **全新架構題**——升級模型＋多案＋使用者拍板（JUDGMENT §6）。
遇到這三類，「明說做不到、把選擇交回使用者」是合格答案。不確定的事說不確定，查不到的說查不到，永遠不要編。
